# 本周交付：答案评估、缓存策略与批量处理

## 交付概览

本周任务是为 MedRAG 项目新增三个模块：答案评估器、缓存策略、批量处理，并用上周实际测试用过的 5 条 metformin query 跑通真实 pipeline 做端到端验证。三项均已完成。

## 一、答案评估部分代码与相关指标

新增 `13_answer_evaluator.py`，包含四个维度的评估指标，最终封装成 `AnswerEvaluator` 类，调用方式为 `evaluator.evaluate(生成的答案, 标准答案)`。

**文本相似性**：使用 `rouge` 库计算 rouge-1 / rouge-2 / rouge-l 的 precision、recall、f1。

**关键信息提取与召回率**：用正则表达式提取六类医学关键字段——百分比、剂量信息、时间范围、安全信息（风险/副作用/不良反应）、治疗建议（建议/治疗/方案）、作用机制（机制/原理/作用）。召回率计算方式为 `recall = overlap / gt_matches`，即生成答案覆盖了多少标准答案中的关键信息。

**幻觉检测**：统计无依据的绝对化表述信号词命中次数（"研究表明""已被证明""100%""完全安全/有效/无害"等），信号词越多风险分越高。

**可读性评估**：按句号/问号/感叹号切分句子，计算平均句子长度和句子数。

## 二、缓存以及批量处理策略代码

新增 `14_cache_manager.py` 和 `15_batch_processor.py`。

**缓存策略**：缓存键为"查询+上下文"的 SHA256 哈希，确保相同输入对应相同缓存键；用 `OrderedDict` 实现 LRU 淘汰机制控制容量上限，避免内存溢出；每条缓存记录带时间戳，超过 TTL（默认24小时）自动失效，考虑到医学知识的时效性不能永久缓存；只有低温度（默认阈值 ≤0.3，即确定性较高）的生成结果才会被缓存，高温度结果每次都不同，缓存没有意义。

**批量处理**：使用 `ThreadPoolExecutor` 并行执行批量生成，worker 数默认按 `os.cpu_count()` 自动调整；单个任务失败通过 `try/except` 隔离，不会影响其他任务正常返回；用 `future_to_idx` 映射保证输出结果顺序与输入 query 顺序严格一致。

## 三、端到端验证结果

新增 `16_test_last_week.py`，接入真实的检索 pipeline（`MedRAGPipeline`）和生成 pipeline（`MedicalGenerationPipeline`，DeepSeek-R1 7B），复用了上周 batch test 用过的 5 条 metformin query（定义在 `12_test_generation_pipeline.py` 的 `TEST_QUERIES` 中）。

第一轮真实生成 5 条 query 耗时 283 秒；第二轮重复运行同样的 query，全部命中缓存，耗时 7.7 秒，验证了缓存机制确实生效。

评估分数中，query 4（"老年患者 metformin 推荐剂量"，即进展文档中记录的"metformin 被误标注成甲磺酸西格列汀"那条已知问题）的 rouge-l f1 和关键信息召回率是 5 条里最低的，明显偏离其他 4 条。虽然评估器目前还没有专门的药物实体核查逻辑，但通用的相似度和关键信息召回已经能间接把这条问题答案识别为异常值，算是意外验证了评估器的实际价值。

## 验证中发现的问题

幻觉检测的信号词列表目前只有中文，而这次生成的答案大多是英文，5 条全部检出 0 风险，需要补充英文版信号词（如 "studies show" "has been proven" "completely safe"）。

本次使用的标准答案（ground truth）是基于通用医学知识现写的草稿，未核对 PMC 原文，评估分数只能定性参考，不能当作准确率数字使用。

批量处理最初用 `max_workers=2` 并发调用检索模块时出现死锁（本地 ChromaDB / embedding 模型可能非线程安全），改成 `max_workers=1` 后恢复正常。本地单机 LLM 场景下并发收益有限，后续如需要真正的并行加速，需要每个 worker 使用独立的 pipeline 实例。
